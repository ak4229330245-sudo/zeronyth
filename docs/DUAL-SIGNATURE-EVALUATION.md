# 二重署名方式（Falcon-1024 ＋ ML-DSA-65 を1取引に同時要求）の評価提案

作成日: 2026-11-05
位置づけ: オーナー指示に基づく**評価・提案のみ**。本方式は実装しない。現行仕様は
「ECDSA / Falcon-1024 / ML-DSA-65 の3方式共存（利用者が選択）」である。

## 1. 評価対象の方式

1つのネイティブ取引に Falcon-1024 と ML-DSA-65 の**両方の署名を必須**とする方式（AND 型）。

- 取引は両方の公開鍵と両方の署名を保持し、検証側は両方を検証して初めて有効とする
- 署名対象は同一の取引ペイロードにドメイン分離した署名メッセージとし、方式間の
  署名の使い回し（クロスプロトコル攻撃）ができないように束縛する
- アドレスは2つの公開鍵の組から導出する（例: `keccak256(falconPk || mldsaPk)` の下位20バイト）

## 2. 取引サイズの評価

コード内定数および各方式の公開仕様に基づく実数：

| 項目 | Falcon-1024 | ML-DSA-65 | 二重署名（合計） |
|---|---|---|---|
| 公開鍵 | 1,793 B | 1,952 B | 3,745 B |
| 署名 | 最大 約1,462 B（可変長） | 3,309 B（固定） | 最大 約4,771 B |
| 鍵＋署名の追加サイズ | 約3.3 KB | 約5.3 KB | **約8.5 KB / 取引** |

影響：

- 通常の ECDSA 取引（全体で 0.1 KB 強）と比べ、二重署名取引は約 8.5 KB の
  鍵・署名データだけで通常取引の数十倍のサイズになる
- 1,000 取引あたり約 8.5 MB の鍵・署名データ。ブロック伝播、TxPool のメモリ、
  チェーンデータの増え方がすべて単独方式の約 1.6〜2.6 倍になる
- ブロックガスリミットが同じなら、取り込める取引数はサイズではなくガスで制限されるが、
  帯域とストレージの観点では二重署名が最も重い

## 3. 処理性能の評価

- 署名検証は2方式分を毎回行う。検証コストは単独方式の単純合計になり、
  TxPool 受付・ブロック取り込みの両方で効く（概算として、一般的な CPU で
  1取引あたり 1 ms 未満のオーダーだが、実装依存のため実測ベンチが別途必要）
- DoS 面：攻撃者は安いコストで「2回検証させる」取引を大量投入できる。
  対策として、両方式分の検証コストとバイト単価を固有ガスに含めることが必須になる。
  それでも単独方式より受付側の CPU 余裕は小さくなる
- 署名生成はウォレット側で2回行う。利用者体験への影響は小さい

## 4. 安全性の評価

利点：

- 偽造には**両方式を同時に破る**必要がある。片方の方式に致命的な脆弱性や
  実装バグが見つかっても、もう片方が残る（単独方式に対する保険になる）

限界（重要）：

- Falcon も ML-DSA も**どちらも格子系**の署名である。格子問題そのものに対する
  根本的な突破が起きた場合、両方同時に弱くなる可能性があり、方式の多様性は
  部分的にしか得られない。本当の意味で独立した保険を求めるなら、ハッシュベース
  署名（SPHINCS+ 等）との組み合わせのほうが多様性は高い（ただし署名サイズはさらに大きい）
- 鍵管理の負担が2倍になり、**どちらか一方の鍵を失うと資産が動かせなくなる**
  （AND 型のため）。可用性リスクは単独方式より明確に高い
- アドレスが鍵の組に束縛されるため、片方の鍵だけをローテーションできない

## 5. 結論と提案

- **通常の送金には二重署名を採用しない**ことを提案する。サイズ（約8.5 KB/取引）、
  検証性能、鍵喪失時の可用性リスクの代償が大きく、得られる安全性の上乗せは
  「格子系同士」という多様性の限界で割り引かれる
- 現行仕様どおり、利用者が Falcon-1024 か ML-DSA-65 を**選択する単独方式**で
  十分な耐量子性が得られる
- 二重署名が本当に必要になるのは「超高額の保管用アカウント」のような限定用途と
  想定する。その場合は取引タイプとして組み込むのではなく、2つの PQ アカウントを
  要求するマルチシグ的な仕組み（コントラクト／アカウント側）で実現するほうが、
  プロトコルを太らせず鍵ローテーションも可能になる
- もし将来プロトコルレベルで実装する場合は、本評価を前提に、有効化ブロック、
  方式別ガス、TxPool の検証上限を設計し、改めてオーナー承認を得ること

（注）本評価の数値は公開仕様とコード内定数に基づく。検証性能の実測ベンチマークは
未実施であり、必要になれば独立テスト環境で取得する。
