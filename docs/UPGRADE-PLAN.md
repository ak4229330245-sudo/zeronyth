## 2. アップグレード手順

1. **バックアップ**：各ノードのデータディレクトリ全体、現行バイナリ一式、
   ジェネシス、鍵ファイル（暗号化済みの現行保管形態のまま）を別領域へ複製。
   チェックサムを記録。
2. **配備**：新バイナリを現行とは別ディレクトリに配置（現行は残す）。
3. **ジェネシス設定の追加**：`pqTxActivationBlock` を追加した設定を用意する。
   有効化ブロックは「全ノード切替完了を確認した時点のチェーン先端＋十分な余裕」
   （目安 +10,000 ブロック ≈ 約2.8時間@1秒間隔）で確定し、全ノードで同一にする。
   ※ この設定キーが無い場合、PQ取引は常時無効（現行本番と同一挙動）であることを
   テスト済み（evidence-nogate.json 5/5）。
4. **ローリング切替**：バリデータ1台ずつ停止→新バイナリで起動→同期とブロック
   取り込みを確認→次台へ。QBFT は 4台中1台の停止に耐えるため、チェーンは
   止めない。各台で `eth_syncing=false` と先端一致を確認してから次に進む。
   RPC/公開ノードがある場合も同様に全台切り替える（ブロック取り込み側も
   新バイナリ必須）。
5. **有効化の監視**：有効化ブロック到達前後で、PQ取引の拒否→受理の切替、
   ECDSA 取引の継続、ブロック生成間隔（約1秒）、アテスターの証明継続を監視。

## 3. ロールバック条件と手順

- **有効化ブロックより前**：いつでも安全に戻せる。問題が出たノードを旧バイナリで
  再起動するだけ（PQ取引はまだ1件も取り込まれていないため互換性の問題なし）。
  全台を戻す場合も同じ手順。
- **有効化ブロック以後**：PQ取引を含むブロックは旧バイナリでは取り込めないため、
  単純なバイナリ巻き戻しは不可。異常時はまずチェーンを止める判断を取り、
  バックアップ時点への復元（データ一式の差し戻し＋全台旧バイナリ）を
  オーナー判断で行う。これが「有効化ブロックに十分な余裕を持たせる」理由。
- 巻き戻しの判断基準（例）：ブロック生成停止が継続する、状態ルート不一致、
  ファイナリティ証明の停止、PQ取引の誤受理・誤拒否の発生。

## 4. 復旧手順（要約）

1. 異常の切り分け（単一ノードか全台か、有効化前か後か）。
2. 有効化前 → 該当ノードを旧バイナリで再起動し同期確認。
3. 有効化後 → オーナーへ即時連絡。全台停止、バックアップからの復元、
   旧バイナリで再起動、整合性確認後に再開。
4. 復旧後は原因が解消されるまで再投入しない。
