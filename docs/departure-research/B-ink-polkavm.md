# B — ink! and the Polkadot Contract Platform: Deep Dive

**Scope for ZERONYTH:** a private chain leaving the Ethereum ecosystem, evaluating a Rust contract stack in the ink! lineage, with DeFi as a core on-chain feature. **Headline verdict up front:** ink!/PolkaVM is an excellent *architectural reference* and a poor *dependency*. The VM transition (Wasm → RISC-V PolkaVM) succeeded and went live on Polkadot Hub in January 2026, but ink! itself never shipped a stable v6, was never audited for v6, and was formally discontinued on 27 January 2026 — the same week Hub contracts launched. Any ZERONYTH adoption would mean forking and self-maintaining the language, or taking the pallet-revive/PolkaVM layer and building a thinner Rust DSL on top of it.

## 1. Architecture: a Rust eDSL, not a new language

ink! is an embedded domain-specific language (eDSL) in ordinary Rust: you write a normal Rust crate annotated with attribute macros — `#[ink::contract]`, `#[ink(storage)]`, `#[ink(constructor)]`, `#[ink(message)]`, `#[ink(event)]` — and proc-macro code generation produces the dispatch, metadata and host-call glue. Contracts run `no_std`, with explicit storage structs and explicit `&self` / `&mut self` message mutability. It originated at Parity in 2018–19 as Polkadot's native Rust contract language (https://4irelabs.com/articles/top-5-challenges-of-building-smart-contracts-with-ink/).

**Compilation target changed completely across versions.** ink! v1–v5 compiled to WebAssembly and executed by `wasmi` inside Substrate's `pallet-contracts`; ink! v6 compiles to RISC-V (`riscv64emac-unknown-none-polkavm`) and executes in PolkaVM inside `pallet-revive` (https://use.ink/docs/v6/background/why-riscv-and-polkavm-for-smart-contracts/ ; https://deepwiki.com/use-ink/ink). Tooling is `cargo-contract`, which drives `rustc` with contract-specific flags, produces the binary plus metadata, and handles upload/instantiate/call.

**Encoding and host interface.** In the native ink! ABI, everything crossing the contract↔host boundary — storage keys and values, message inputs and return values, constructor arguments — is SCALE-encoded (`parity-scale-codec`), passed through a pre-allocated static buffer (16 kB in v6) to avoid heap allocation on the hot path (https://deepwiki.com/use-ink/ink/1.1-architecture). Contracts do not touch chain state directly; they call host functions exposed by the pallet (via `pallet-revive-uapi` in v6) for storage, caller/balance/block queries, transfers, hashing, events and cross-contract calls, returning via `seal_return`. The off-chain engine mirrors the same API, so unit tests run the contract logic in-process in Rust, and `ink_e2e` runs the compiled binary against a real runtime.

**Evolution in brief.** v4/v5 matured the model: v5 (March 2024) made returning `Err` from a message revert state — Solidity-like revert semantics — closing gaps from an OpenZeppelin security review, and allowed events to be defined in separate crates and shared (https://4irelabs.com/articles/top-5-challenges-of-building-smart-contracts-with-ink/). Persistent weaknesses were also structural: macro-heavy code is hard to debug, and standard-library equivalents were thin — OpenBrush (by Brushfam) was ink!'s OpenZeppelin analogue, and Brushfam later stepped back from Polkadot, leaving OpenBrush's future uncertain (same source).

## 2. ink! v6 — and a necessary correction on "async"

v6 is defined by one breaking migration: "`pallet-contracts` + WebAssembly (executed in `wasmi`) to `pallet-revive` + RISC-V (executed in PolkaVM)"; v6 requires `cargo-contract >= 6` and a chain containing `pallet-revive` (https://use.ink/docs/v6/faq/migrating-from-ink-5-to-6/). Around that migration, revive's Ethereum-first design was imposed on ink!, explicitly: the v6 alpha notes state "the `pallet-revive` team has Ethereum/Solidity support as the number one priority. All their design decisions derive from that" (https://github.com/use-ink/ink/releases/tag/v6.0.0-alpha). Concretely:

- **Ethereum-shaped types:** balance contexts use `U256`, contract addresses become `Address`/`H160` (20-byte, with a required 1-to-1 `AccountId ↔ H160` mapping via `map_account`), hashes become fixed `H256` (https://use.ink/docs/v6/faq/migrating-from-ink-5-to-6/).
- **Solidity ABI as a first-class mode:** `abi = "ink" | "sol" | "all"` in `Cargo.toml` metadata; in `sol`/`all` mode an ink! contract is callable from Solidity, MetaMask and Hardhat, and `CallBuilder` can call Solidity-ABI contracts — at the cost of restricting public types to those with Solidity mappings and larger binaries in dual-ABI mode (same source).
- **Removals:** `call_runtime` and chain extensions are gone — runtime functionality must now be exposed as precompile contracts called via cross-contract/delegate calls; delegate calls now target an instantiated contract *address*, not a code hash; most pallet contract events were removed by Parity; Solang support ended in favour of Parity's `revive`/`resolc` Solidity→RISC-V compiler; `substrate-contracts-node` was replaced by `ink-node` (same source).
- **Precompiles as the extension mechanism:** the Alliance implemented/used Polkadot SDK precompiles (XCM, Assets, etc.) in ink!, i.e. system functionality is reached as if it were another contract (https://forum.polkadot.network/t/discontinuation-of-ink-rust-smart-contract-language/16849).

**On async/await — the premise needs correcting.** On-chain ink! messages are *not* async. Execution is synchronous and deterministic: a cross-contract call is a blocking host call built with `build_call`/`CallBuilder` and fired with `invoke()`/`try_invoke()`, returning a value or a handleable `LangError` in the same call frame (https://use-ink.github.io/ink/ink_env/call/fn.build_call.html). That is precisely the EVM-like synchronous composability DeFi relies on (a DEX contract calling a token's `transfer_from` inline, atomically). Async exists at two *other* layers: (1) the client/test side — `#[ink_e2e::test]` functions are `async fn`, and deployment/calls are `.submit().await` against a node (https://deepwiki.com/use-ink/ink/5.2-end-to-end-testing); and (2) PolkaVM's design goal of cheap "asynchronous gas metering" (https://github.com/paritytech/polkavm). Cross-*chain* interaction, where present, goes through XCM precompiles — Polkadot's message-passing protocol — not through a language-level async contract model. So the programming model v6 enables is: **ordinary Rust + synchronous, type-safe cross-contract calls (via generated `ContractRef`/trait definitions or the low-level `CallBuilder`), with an async Rust client/test harness** — not async contracts.

## 3. Current status and roadmap: pallet-contracts → pallet-revive, Wasm → PolkaVM

**Why Parity abandoned Wasm.** The Polkadot Wiki lists Wasm's flaws as non-deterministic execution risk and high translation cost: Wasm is stack-based while hardware is register-based, making register allocation expensive (https://wiki.polkadot.com/learn/learn-smart-contracts/). The ink! docs add that Parity had researched alternatives (including eBPF) for years; in 2023 Parity developer Jan Bujak (@koute) explored RISC-V and started PolkaVM (https://use.ink/docs/v6/background/why-riscv-and-polkavm-for-smart-contracts/).

**PolkaVM's rationale.** PolkaVM ingests normal RISC-V ELF binaries from standard compilers and translates them offline into a constrained custom bytecode — its lead explains it is "not actually a RISC-V VM" running binaries as-is, that code addresses are fully virtualised, and that it gets "very close to bare metal performance… as fast as `wasmtime`… but guarantees O(n) recompilation and recompiles programs… hundreds [of] times faster" (http://ethereum-magicians.org/t/long-term-l1-execution-layer-proposal-replace-the-evm-with-risc-v/23617/32). The repo's design goals echo this: sandboxed-by-default in a separate process, fully deterministic, ≤128 KB baseline memory per instance, single-pass O(n) compilation, and a spec simple enough to re-implement an interpreter in under a week — while candidly warning "not all of these are currently true" and "Do not use it in production!" at repo level (https://github.com/paritytech/polkavm). The Wiki notes the deployment staging: initially the PolkaVM *interpreter* runs inside the runtime; a full JIT in the client comes later (https://wiki.polkadot.com/learn/learn-smart-contracts/). PolkaVM is also the execution substrate specified for JAM, Polkadot's planned relay-chain successor, so the VM bet is bigger than contracts alone.

**pallet-revive's shape in 2026.** Parity forked `pallet-contracts` into `pallet-revive` in late 2024, changing types/events/debugging to be Solidity-compatible and adding an Ethereum RPC wrapper (https://use.ink/docs/v6/background/why-riscv-and-polkavm-for-smart-contracts/). By 2026 the official Polkadot docs describe a **dual-VM stack**: REVM (a Rust EVM) runs unmodified Solidity bytecode, while the PVM backend runs `resolc`-compiled Solidity and Rust for performance — "Most developers should start with REVM… PVM is available for projects with specific performance requirements," and for Rust on PVM, "Tooling is still limited" (https://docs.polkadot.com/smart-contracts/for-eth-devs/dual-vm-stack.md). Parity's launch post (27 Jan 2026) confirms smart contracts went live natively on Polkadot Hub (Asset Hub) that month, after a Kusama trial, with EVM and PVM contracts interoperating (https://www.parity.io/blog/why-developers-should-deploy-smart-contracts-on-polkadot). One secondary tally put deployments at ~19 contracts a week after launch (https://coinstats.app/ai/a/fundamental-analysis-polkadot).

**What is stable vs in flux.** Stable/live: `pallet-revive` on Kusama and Polkadot Hub, REVM Solidity path with MetaMask/Hardhat/Foundry, Ethereum JSON-RPC via the `eth-rpc` adapter (https://docs.polkadot.com/parachains/customize-runtime/add-smart-contract-functionality/). In flux/unfinished: PolkaVM JIT, PVM tooling maturity, ink! v6 itself (beta, unaudited, and — per the Alliance — its beta binaries are *not compatible* with the `pallet-revive` Parity only stabilised in December 2025) (https://forum.polkadot.network/t/discontinuation-of-ink-rust-smart-contract-language/16849).

## 4. Current problems and reality

- **ink! v6 never reached production.** As of late 2025 it was "currently in an unoptimised beta state," dependent on a paused security audit and on PolkaVM's Hub launch (https://forum.polkadot.network/t/ink-status-context-and-why-it-matters-for-polkadot/16456). It then never got the audit or a stable release.
- **Funding/governance failure, not a technical verdict.** Three OpenGov proposals (Refs 1760, 1773, 1796) were rejected despite shrinking scope; the Alliance worked unpaid Sep–Dec 2025; on 23 Jan 2026 W3F/Parity confirmed no strategic case, and ink! was "formally deprioritised as an official ecosystem initiative" and discontinued (https://forum.polkadot.network/t/discontinuation-of-ink-rust-smart-contract-language/16849 ; https://polkadot.subsquare.io/referenda/1760). The Alliance's own advice to builders awaiting Hub deployment: use `pallet-revive`'s low-level Rust API (explicitly *not recommended* for a general audience) or rewrite in Solidity (same forum post).
- **Adoption was always thin.** Community debate conceded low adoption, Rust's learning curve, `cargo-contract` lagging Hardhat/Foundry, missing OpenZeppelin-grade libraries and few flagship dApps (https://forum.polkadot.network/t/what-do-you-think-should-we-push-ink-or-move-with-solidity/14031.rss). Developer surveys cited lack of liquidity/users, immature tooling and "not too many parachains support ink!" (https://hackmd.io/@s_iGZLIITG6WjSgnFX0pcg/rJJZgc2S6).
- **The largest ink! host is exiting.** Astar — historically the biggest ink! dApp chain — froze new Wasm uploads in runtime-2207 (June 2026), citing discontinuation, `pallet-contracts` as legacy, and unmaintained code as a growing security liability; its own census found only 305 live contracts and 3,101 all-time unique callers on Astar, last deployment Nov 2025 (https://forum.astar.network/t/wasm-smart-contract-sunset-on-astar-and-shiden/9516).

## 5. The central debate: ink!/Rust vs Solidity/EVM

**For ink!/Rust:** the Alliance's "Rust > Solidity: Data Doesn't Lie" argued from Electric Capital data that Rust ecosystems onboard developers ~30% faster, that Rust-based contracts represent 45.5% of top-20 ecosystems vs 40.9% EVM, and that ink! was "the only PolkaVM-compatible smart contract language at Hub launch" — plus Rust type safety, with one ZK-verifier example claiming ~25% gas saving and 45% smaller binary vs Solidity (https://forum.polkadot.network/t/rust-solidity-data-doesn-t-lie/15683 ; https://forum.polkadot.network/t/ink-status-context-and-why-it-matters-for-polkadot/16456). Dual-track supporters argued the Hub should onboard via *both* Solidity and ink! (https://forum.polkadot.network/t/what-do-you-think-should-we-push-ink-or-move-with-solidity/14031.rss).

**For Solidity-first:** Parity designed `pallet-revive` with "Ethereum/Solidity support as the number one priority" (https://github.com/use-ink/ink/releases/tag/v6.0.0-alpha), because Solidity brings the existing developer base, audited patterns, OpenZeppelin, MetaMask/Hardhat/Foundry and ethers.js with no new language to learn; governance voters repeatedly declined to fund a second, common-good language stack, and Parity "could not determine sufficient strategic reason to include ink! in the Polkadot Hub roadmap" (https://forum.polkadot.network/t/discontinuation-of-ink-rust-smart-contract-language/16849).

**What was decided:** not a merge, but a sequencing that became a verdict. Technically, both languages *do* share one VM — revive compiles Solidity to PVM, ink! v6 added a Solidity ABI, and by 2026 REVM was added so unmodified EVM bytecode also runs, with cross-calls between backends (https://docs.polkadot.com/smart-contracts/for-eth-devs/dual-vm-stack.md). Institutionally, Solidity won: it is Parity's funded, documented default path, while ink! lost funding, maintainership and its main host chain within six months of Hub launch.

## 6. Implications for ZERONYTH

1. **Copy the layering, not the dependency:** Rust eDSL → SCALE-or-ABI encoding → host functions → register-based VM is a proven, clean design; but pinning ZERONYTH DeFi to upstream ink! v6 means inheriting an unaudited beta incompatible with current `pallet-revive`.
2. **Budget for ownership:** the Polkadot experience shows a contract language is permanent common-good infrastructure; if ZERONYTH adopts this lineage, it must fund the language, audit and tooling itself, indefinitely.
3. **Synchronous composability is the DeFi-relevant property** — and ink!/revive has it. There is no async contract model to import.
4. **PolkaVM is the more durable asset:** it survived the debate (Hub + JAM), whereas Wasm/`pallet-contracts` and ink! did not. Evaluate PolkaVM/revive directly, with a thin in-house Rust DSL, before evaluating ink! as a product.
